# Benchmark A/B: Postgres vs Oracle vs SQL transpilado — 2026-10-23

*[English](2026-10-23-ab.md)*

¿Un modelo local escribe SQL correcto para Oracle igual que para Postgres, o conviene pedir Postgres y transpilar? Esta corrida mide la **exactitud de ejecución**: una consulta es correcta si su resultado es igual al de la consulta de referencia en la misma base. Datos crudos: [`2026-10-23/results.json`](2026-10-23/results.json). Arnés: `python -m scripts.bench_ab` (PR #16).

## Montaje

| | |
|---|---|
| Estrategias | `pg_direct` (prompt y documentos de Postgres, se ejecuta en Postgres), `oracle_direct` (prompt y documentos de Oracle, se ejecuta en Oracle), `pg_transpiled` (prompt de Postgres, `sqlglot` 25.24.0 transpila a Oracle, se ejecuta en Oracle) |
| Modelos | `sqlcoder:latest` (digest `77ac14348387`), `qwen2.5-coder:7b` (digest `dae161e27b0e`), temperatura 0, una corrida cada uno |
| Datos | Sintéticos y deterministas (semilla 42): 300 clientes, 2000 facturas, 1486 pagos, 1117 acciones de cobro, cargados igual en ambas bases (sumas de control en el JSON) |
| Bases | `pgvector/pgvector:pg16`; `gvenzl/oracle-free:23.26.3-slim-faststart`, cuenta de solo lectura `APP_RO`, formatos de fecha ISO en la sesión |
| Preguntas | 30 en español, cada una con consulta de referencia por dialecto; las referencias dan resultados iguales en ambas bases |
| Pipeline | El real: recuperación de esquema (reindexado por dialecto), generación de SQL, cortafuegos AST, ejecución con timeout |

Puntuación: *estricta* = mismas filas, mismas columnas y mismo orden de columnas (filas como multiconjunto salvo que la pregunta sea ordenada). *Relajada* = la estricta, o las columnas esperadas aparecen entre columnas extra o en otro orden. Intervalos de Wilson al 95 %.

## Qué dicen los datos

1. **El modelo pesa mucho más que el dialecto.** `qwen2.5-coder:7b` saca 19–22 donde `sqlcoder` saca 7–8. Esa brecha queda fuera de los intervalos.
2. **Postgres directo y Oracle directo no se distinguen con esta muestra** (22 vs 21 en qwen, 8 vs 8 en sqlcoder). Los intervalos se solapan casi por completo. Pregunta a pregunta sí difieren: en qwen solo `q25` (mediana) se resolvió en Postgres y no en Oracle; en sqlcoder las diferencias van en los dos sentidos (3 preguntas cada uno).
3. **Transpilar cuesta algo, y el costo se concentra en las fechas.** En qwen, `pg_transpiled` perdió 3 preguntas que `pg_direct` resolvía y no ganó ninguna:
   - `q06` y `q21` (`DATE_TRUNC`): sqlglot emite `TIMESTAMP_TRUNC`, que Oracle no tiene (`ORA-00904`).
   - `q16` (promedio de días entre dos fechas): `::date` pasa a `CAST(... AS DATE)`, que en Oracle conserva la hora, así que la consulta se ejecuta y devuelve un **número equivocado sin error**. Es el modo de fallo peligroso.
   En sqlcoder la pérdida es 1 pregunta (`q21`). Tres preguntas está dentro del ruido con n = 30, pero el mecanismo es claro, se reproduce con las consultas de referencia y no depende del modelo: el techo del transpilador en este conjunto es 27/30 incluso con SQL perfecto.
4. **Muchos fallos no tienen que ver con el dialecto.** Ejemplos con qwen en las tres estrategias: las preguntas de top-N (`q12`, `q14`), «más de un pago» (`q22`) y las de subconsulta/join (`q29`, `q30`) devuelven un resultado verosímil pero equivocado. `q08` falla con `ORA-00904`/`UndefinedColumn` porque el modelo inventó una columna (`registration_date`), no por la transpilación. `q23` falla en Postgres porque el modelo restó un intervalo a un literal de texto.
5. **También hay fallos propios de Oracle en la ruta directa.** El `LISTAGG` de qwen sobre todas las filas de pagos (`q27`) desborda el límite de cadena (`ORA-01489`); su consulta de mediana para `q25` (`CONNECT BY` más sintaxis inventada) ni siquiera se parsea y se rechaza antes de ejecutar.

## Taxonomía de errores

| Código | Veces (todas las corridas) | Causa típica |
|---|---|---|
| `ORA-00904` | 12 | `TIMESTAMP_TRUNC` tras transpilar (3); identificadores inventados o mal calificados (8); `DATE_PART` sin traducir (1) |
| `UndefinedColumn` (Postgres) | 4 | columnas inventadas |
| `ORA-00979`, `ORA-30089`, `ORA-01489`, `InvalidDatetimeFormat` | 1 cada uno | `GROUP BY` incorrecto, sintaxis de intervalo, desborde de `LISTAGG`, intervalo sobre texto |

## Limitaciones

- **n = 30.** Las diferencias menores de unos 15 puntos porcentuales no son concluyentes. No leas 22 vs 21 como un ranking.
- **El autor redactó las preguntas y el SQL de referencia.** No es un benchmark público y se eligieron incluyendo trampas de dialecto (fechas, agregación de texto, medianas), así que los números absolutos dicen poco sobre la calidad general de texto a SQL.
- **Una corrida por celda, temperatura 0.** No se midió la varianza entre corridas.
- **Dos modelos locales pequeños.** Modelos más grandes o alojados pueden comportarse distinto, y los prompts no se afinaron por dialecto más allá de los del proyecto.
- **Datos sintéticos en un esquema pequeño** (cuatro tablas).
- Oracle Free 23ai y cuenta de solo lectura; otras ediciones u otros ajustes de sesión pueden dar resultados distintos.

## Reproducir

```bash
docker compose -f docker-compose.yml -f docker-compose.oracle.yml up -d --wait db oracle
python - <<'PY'
from scripts import gen_dataset
d = gen_dataset.generate(); gen_dataset.load_postgres(d); gen_dataset.load_oracle(d)
PY
python -m scripts.bench_ab --out-json results.json --out-md report.md
```

`--llm gold` y `--llm wrong` validan el propio arnés: el SQL de referencia saca 30/30 en las dos estrategias directas y 27/30 transpilada; `SELECT 1` saca 0.
