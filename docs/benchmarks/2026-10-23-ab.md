# A/B benchmark: Postgres vs Oracle vs transpiled SQL — 2026-10-23

*[Español](2026-10-23-ab.es.md)*

Does a local model write correct SQL for Oracle as well as for Postgres, and is it better to ask for Postgres and transpile? This run measures **execution accuracy**: a query counts as correct when its result equals the result of the reference query on the same database. Raw data: [`2026-10-23/results.json`](2026-10-23/results.json). Harness: `python -m scripts.bench_ab` (PR #16).

## Setup

| | |
|---|---|
| Strategies | `pg_direct` (Postgres prompt and docs, runs on Postgres), `oracle_direct` (Oracle prompt and docs, runs on Oracle), `pg_transpiled` (Postgres prompt, `sqlglot` 25.24.0 transpiles to Oracle, runs on Oracle) |
| Models | `sqlcoder:latest` (digest `77ac14348387`), `qwen2.5-coder:7b` (digest `dae161e27b0e`), temperature 0, one run each |
| Data | Synthetic and deterministic (seed 42): 300 customers, 2000 invoices, 1486 payments, 1117 collection actions, loaded identically in both databases (checksums in the JSON) |
| Databases | `pgvector/pgvector:pg16`; `gvenzl/oracle-free:23.26.3-slim-faststart`, read-only `APP_RO` account, ISO session date formats |
| Questions | 30 in Spanish, each with a reference query per dialect; the references return equal results on both databases |
| Pipeline | The real one: schema retrieval (re-indexed per dialect), SQL generation, AST firewall, execution with timeout |

Scoring: *strict* = same rows, same columns, same order of columns (rows as a multiset unless the question is ordered). *Relaxed* = strict, or the expected columns appear among extra or reordered columns. Intervals are 95 % Wilson.

## Results

| Model | Strategy | Strict (k/30) | 95 % CI | Relaxed (k/30) | Execution errors | Firewall rejections |
|---|---|---|---|---|---|---|
| qwen2.5-coder:7b | `pg_direct` | **22** | 56–86 % | 24 | 2 | 0 |
| qwen2.5-coder:7b | `oracle_direct` | **21** | 52–83 % | 23 | 2 | 1 |
| qwen2.5-coder:7b | `pg_transpiled` | **19** | 46–78 % | 21 | 4 | 0 |
| sqlcoder | `pg_direct` | **8** | 14–44 % | 12 | 3 | 1 |
| sqlcoder | `oracle_direct` | **8** | 14–44 % | 10 | 5 | 0 |
| sqlcoder | `pg_transpiled` | **7** | 12–41 % | 11 | 4 | 0 |

## What the data says

1. **The model matters far more than the dialect.** `qwen2.5-coder:7b` scores 19–22 where `sqlcoder` scores 7–8. That gap is well outside the intervals.
2. **Direct Postgres and direct Oracle are indistinguishable at this sample size** (22 vs 21 for qwen, 8 vs 8 for sqlcoder). The intervals overlap almost completely. Per question they do differ: for qwen only `q25` (median) was solved on Postgres and not on Oracle; for sqlcoder the differences go both ways (3 questions each way).
3. **Transpiling costs something, and the cost is concentrated in dates.** For qwen, `pg_transpiled` lost 3 questions that `pg_direct` solved and gained none:
   - `q06` and `q21` (`DATE_TRUNC`): sqlglot emits `TIMESTAMP_TRUNC`, which Oracle does not have (`ORA-00904`).
   - `q16` (average days between two dates): `::date` becomes `CAST(... AS DATE)`, which in Oracle keeps the time of day, so the query runs and returns a **wrong number with no error**. This is the dangerous failure mode.
   For sqlcoder the loss is 1 question (`q21`). Three questions is inside the noise for n = 30, but the mechanism is clear, reproduced from the reference queries, and independent of the model: the ceiling of the transpiler on this question set is 27/30 even with perfect SQL.
4. **Many failures are not about the dialect.** Examples with qwen on all three strategies: top-N questions (`q12`, `q14`), "more than one payment" (`q22`), and the two subquery/join questions (`q29`, `q30`) return a plausible but wrong result. `q08` fails with `ORA-00904`/`UndefinedColumn` because the model invented a column (`registration_date`), not because of transpilation. `q23` fails in Postgres because the model subtracted an interval from a string literal.
5. **Oracle-specific failures exist on the direct path too.** qwen's `LISTAGG` over every payment row (`q27`) overflows the string limit (`ORA-01489`); its median query for `q25` (`CONNECT BY` plus invented syntax) does not even parse and is rejected before execution.

## Error taxonomy

| Code | Count (all runs) | Typical cause |
|---|---|---|
| `ORA-00904` | 12 | `TIMESTAMP_TRUNC` after transpiling (3); invented or wrongly qualified identifiers (8); untranslated `DATE_PART` (1) |
| `UndefinedColumn` (Postgres) | 4 | invented columns |
| `ORA-00979`, `ORA-30089`, `ORA-01489`, `InvalidDatetimeFormat` | 1 each | bad `GROUP BY`, interval syntax, `LISTAGG` overflow, interval on a string |

## Limitations

- **n = 30.** Differences smaller than about 15 percentage points are not conclusive. Do not read 22 vs 21 as a ranking.
- **The author wrote the questions and the reference SQL.** They are not a public benchmark, and they were chosen to include dialect traps (dates, text aggregation, medians), so absolute numbers say little about general text-to-SQL quality.
- **One run per cell, temperature 0.** Run-to-run variance was not measured.
- **Two small local models.** Larger or hosted models may behave differently, and the 7B model's prompts were not tuned per dialect beyond the project's own.
- **Synthetic data in a single small schema** (four tables).
- Oracle Free 23ai and a read-only account; results on other editions or with other session settings may differ.

## Reproduce

```bash
docker compose -f docker-compose.yml -f docker-compose.oracle.yml up -d --wait db oracle
python - <<'PY'
from scripts import gen_dataset
d = gen_dataset.generate(); gen_dataset.load_postgres(d); gen_dataset.load_oracle(d)
PY
python -m scripts.bench_ab --out-json results.json --out-md report.md
```

`--llm gold` and `--llm wrong` validate the harness itself: reference SQL scores 30/30 on both direct strategies and 27/30 transpiled; `SELECT 1` scores 0.
