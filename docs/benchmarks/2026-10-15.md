# Benchmark con infraestructura real — 2026-10-15

Primera corrida de `POST /query` contra Postgres + pgvector y Ollama reales (hasta ahora todo se probaba con mocks).
Compara la versión **antes** de la optimización (`d285a58`, `main` previo al PR #6) con la **después** (`ec80205`, tras #6–#8).
Datos crudos en [`2026-10-15/`](2026-10-15/).

## Entorno
| | |
|---|---|
| Máquina | Laptop, RTX 4060 Laptop (8 GB VRAM), WSL2 |
| LLM | Ollama 0.40.4, `sqlcoder:latest` (4.1 GB, 100 % en GPU, precargado antes de cada corrida) |
| Base | `pgvector/pgvector:pg16` (PostgreSQL 16.15, pgvector 0.8.7), `db/schema.sql` + `db/seed.sql` (3 clientes, 4 facturas) |
| Embeddings | `paraphrase-multilingual-MiniLM-L12-v2`, CPU |
| Índice | 6 fragmentos (4 tablas + 2 ejemplos), `python -m scripts.index_schema` |
| Herramientas | `python -m scripts.bench_query` (latencia por pregunta y etapa) y `scripts/load_test.py` (Locust, 10 usuarios, 2 min) |

## Resultados

| Métrica | Antes | Después |
|---|---|---|
| Base inalcanzable (IP que no responde) | **HTTP 500 en 138.5 s** | **HTTP 503 en 4.0 s** |
| Preguntas fuera del dominio (3) | 2 × 200 con SQL inventado, 1 × 400; p50 1000 ms | 3 × 422 sin llamar al LLM; p50 16 ms |
| Primer request tras arrancar | 3520 ms | 1236 ms (modelo de embeddings precargado) |
| Arranque hasta `/health` | 5.0 s | 6.1 s (paga el warm-up al arrancar) |
| Pregunta de dominio en frío, p50 (9) | 1188 ms | 1122 ms |
| Misma pregunta en caché, p50 (10) | 4.3 ms | 3.8 ms |
| Locust `/query`, mediana / req/s | 7 ms / 4.6 | 7 ms / 4.5 |

Lectura:
- **Fallas de infraestructura**: el `connect_timeout` y el mapeo a 503 convierten un cuelgue de más de dos minutos en una respuesta en 4 s.
- **Fuera del dominio**: antes, "¿Cuál es la capital de Francia?" generaba `SELECT … FROM customers WHERE country = 'France'` y lo ejecutaba (200). Ahora se rechaza antes del LLM, ~60× más rápido.
- **Camino feliz**: sin cambio relevante (lo domina el LLM). El warm-up mueve ~2.3 s del primer request al arranque.
- **Locust no distingue las versiones**: con 10 preguntas fijas, tras la primera ronda todo sale del cache en memoria, así que mide el cache (~7 ms), no el pipeline. Para medir carga real hacen falta preguntas no repetidas.

### Desglose por etapa (después, en frío; header `Server-Timing`)
En las 8 respuestas 200 tras el primer request, el LLM es ~98 % de la latencia: `llm` 829–2179 ms, `retrieval` 10–16 ms (360 ms en el primer request), `db` 2–3 ms, `validate` < 2 ms.

## Calidad del SQL generado (revisión manual, 10 preguntas de `scripts/questions.py`)
**3 de 10 correctas** (1, 4, 10). Las demás:

| # | Pregunta | Problema |
|---|---|---|
| 2 | Monto total pagado por cliente | SQL que no parsea → 400 |
| 3 | Facturas pendientes | Usa `status = 'overdue'` y cuenta clientes en vez de listar facturas |
| 5 | Acciones de cobranza sobre vencidas | Agrega `> 30 días` copiado del ejemplo recuperado (limitación del Módulo 4 de NOTES) |
| 6 | Pagos parciales último mes | Inventa `payment_method = 'partial'`; el esquema no tiene ese concepto |
| 7 | Promedio de días emisión→pago | Devuelve filas en vez de `AVG`, con la resta invertida |
| 8 | Clientes sin pagos | JOIN equivocado (`customer_id = payments.invoice_id`) |
| 9 | Facturas por mes último año | Cuenta clientes del mes actual, sin `GROUP BY` mes |

La latencia y la robustez ya no son el cuello de botella: lo es la **exactitud semántica**.

## Calibración del umbral `MAX_SCHEMA_DISTANCE` (0.7)
Distancia coseno mínima del retrieval con la base real (23 preguntas):

- Dominio (15): 0.321–0.651, y un caso en **0.817** ("¿Cuánto debe Ana Torres?").
- Fuera del dominio (8): **0.777**–1.029.

Con 0.7, "¿Cuánto debe Ana Torres?" (legítima) se rechaza como fuera del dominio. Los rangos se solapan (0.777–0.817), así que ningún umbral los separa con este índice. Opciones: mejorar la señal semántica de `data/schema_docs/tables.md` (ya anotado como mejora en `app/core/retrieval.py`), o usar el umbral solo como filtro grueso (~0.85) y aceptar que algo fuera del dominio llegue al LLM.

## Cómo reproducir
```bash
docker run -d --name text2sql-pg -e POSTGRES_PASSWORD=postgres -p 127.0.0.1:5432:5432 pgvector/pgvector:pg16
docker exec -i text2sql-pg psql -U postgres < db/schema.sql
docker exec -i text2sql-pg psql -U postgres < db/seed.sql
python -m scripts.index_schema
ollama pull sqlcoder
uvicorn app.main:app --port 8000          # en otra terminal
python -m scripts.bench_query --host http://localhost:8000 --out bench.json
locust -f scripts/load_test.py --headless -u 10 -r 2 -t 2m --host http://localhost:8000 --csv locust
```
Base inalcanzable: arrancar el server con `DATABASE_URL=postgresql://postgres:postgres@10.255.255.1:5432/postgres` y hacer un `POST /query`.
